# Lanternfall architecture

The published game is one HTML file, `dist/lanternfall.html`, built from `src/`.
Never edit `dist/` by hand.

What the game is and why: `docs/GAME.md` (every live system and its files) and `docs/DECISIONS.md` (owner decisions).
Spec names below that no longer exist in `docs/design/` (deepwell.md, combat-2.md, solo-hero.md, onboarding.md and the
like) were retired on 2026-10-02; read one with `git show 1536ffa:docs/design/<name>.md`. The same goes for spec names
in code comments.

## Build

`tools/build.mjs` = `src/shell.html` with `<!-- @styles -->` replaced by every
`src/styles/*.css` (filename order) in one `<style>`, and `<!-- @script -->` replaced by every
`src/js/*.js` (filename order) concatenated inside one `(() => { 'use strict'; ... })()`.
All JS files share one scope: top-level `const`/`function` in one file is visible to later files.

Each tab opens as a full-screen menu (portrait) or a panel over the right part of the stage (landscape and desktop, UX-L1) and is split
into 2-4 **sub-views** (docs/design/layout.md has the map). Adding a system: pick a view, never append
to a tab's end.
```js
registerSection(tabId, { id, title, view, mount(el), update(force) }) -> el
  // tabId: adv|party|gat|forge|world, camp|tav|raid (the Camp tab's parts, each its own view), or log (bell sheet, Journal)
  // view: a registerView id; omitted = the tab's first view. A new id makes a new view (label = title).
registerView(tabId, { id, label, order = 50, dot, feature, show }) -> view   // a sub-view button; lowest order first (the default)
  // show() -> false leaves the view out of the switcher for now (UX-A: Mining on a cold Hearth)
  // dot() -> true: attention dot on the button (and the tab) while that view is not open. Keep it cheap.
setTab(tabOrViewId, sel?)   // open a menu; a view id ('bounties', 'raid', 'make') opens that view; sel picks the view holding it and scrolls there
closeMenu()                 // back to the game view (both layouts). S.tab is '' while no menu is open
registerTab({ id, label, icon, mount(panel), update(force), hidden }) -> panel   // a sixth tab: avoid, prefer a view
  // hidden: true = a full-screen menu with no tab button (the Achievements menu, id 'deeds'): open it with
  // setTab(id) or one of its view ids; sections and views register on it like any tab (lazy mount)
```
```js
registerSection('adv', { id: 'bounty', title: 'Bounties', view: 'bounties',
  mount(sec) { sec.append(el('p', null, 'Kill 50 foes.')); },  // el() helper from 60-gfx
  update(force) { /* ~5x per second while its tab and view are open */ } });
registerView('forge', { id: 'salvage', label: 'Salvage', order: 25, dot: () => bagFull() });
```
Static markup in `src/shell.html` joins a view with `data-view="id"` on the panel's direct child
(`"*"` = every view, or a space-separated list). Sections only update while their view shows, so rows
built in `update()` may not exist yet; `setTab(tab, sel)` builds them once before it looks for `sel`.
`mount(sec)` does not run at load: it runs when the section's tab first opens, always in registration
order within the tab: the sections up to the last one of the view that opens mount at once, the rest
of the tab in the next tasks (`log` sections when the Journal first shows; `setTab(tab, sel)` mounts
the whole tab at once). The section's own element exists from registration. Keep event handlers
(`on(...)`) outside `mount`, and never rely on nodes that `mount` builds before the tab has opened.

```js
registerGoal({ id, sys, label, pct, go, icon, prio }) -> remove()   // a "Next up" goal (55-goals.js)

```
`pct()` returns progress 0..1 (>= 1 = ready, shown first; null or <= 0 hides it); keep it cheap.
`label` is a string or fn. `sys` groups goals: at most 1-2 per system are shown. `go` is
`{ tab, view, sel, fn }` (the UI runs `fn`, opens the tab's menu on the view that holds `sel`, or on
`view` when there is no `sel`, scrolls to `sel` and flashes it) or a fn
returning one. `icon` is a toast icon spec, or `{ mob: typeKey }` / `{ char: rosterId }`.
`prio` (default 0) breaks ties and orders ready goals. Register from your own 55-*.js file.
`cap: 1` (optional): the diversity pass never takes a second goal from that `sys` (the deeds nudge, the story chapter).
`reserve: 1` (optional): when the goal has something to show it keeps one of the 3 rows (it replaces the lowest other
pick), so Ready goals cannot crowd it out (the deeds nudge, AP6). At most one reserved row.

## How the checks work

`node tools/build.mjs` then `node tools/check.mjs` must both pass before a branch is done.

- **The game is solo.** `tools/check.mjs`, `tools/sim.mjs` and `tools/perf.mjs` test the game players get. The party build, its
  `SOLO_TUNE.on` switch, the `__SOLO` prelude and the `--party` flag are deleted (W3-A). `check.mjs` loads the core in a Node vm
  (`tools/lib/core.mjs`); the browser sections drive `dist/lanternfall.html` in headless Chromium (Playwright).
- **Sections.** Each section is `if (section('name')) try { ... } catch (e) { fail(...) }`: a heading, then `assert(cond, message)` lines.
  Shared systems (economy, gear, crafting, gathering, tools, camp, cold Hearth, deeds, notices, Deepwell, stars, Codex, raid, save codes,
  error capture, nav, store, Hands) and the solo hero (`solo hero`, guide, copy, effects, notices, hero art) run on solo. A section that
  needs a hero calls `soloPick("wren" | "tobin" | "pip")` first (a new game has none until the picker).
- **Removed systems stay removed.** The `removed systems (W2-C)` section greps `src/` for the globals, save fields and CSS of the deleted pinnacle bosses, legendary powers and circle sets, and expeditions (and the Map Room), and opens every tab in Chromium with no console error. Add a name to its `RE` when you delete another system. W3-C adds a second list (`RE3`): no old-save code (`migrate*`, `storeMigrate`, the `oldSave` shortcut), no undefined global (`heroAsk`), and no party leftover (`outOf`, `FORM_TUNE`, the Show targets toggle). To vet a new name, run eslint `no-undef` over the script in `dist/lanternfall.html`.
- **Fixtures.** `tests/fixtures/save-{early,mid,late}.json` are v5 saves the game wrote (`node tools/sim.mjs --policy mixed --hours 1 --class ranger --every 600 --snap 20:early.json`; `--days 4 --class warden --snapday 4:mid.json`; `--days 60 --class lanternmage --snapday 60:late.json`, then load it in `loadCore`, set `S.maxZone = 38`, tick and `save()`: the hero cannot reach the coast on its own yet). Regenerate them on every save-key bump. The `saves` section also checks that an older key, garbage and `{}` start a fresh game.
- **Speed.** By default the run splits into `--jobs=N` child processes (4 with 4 cores); every child walks the same sections in the same
  order and the lightest shard takes each one (`WEIGHT` in `check.mjs` holds the measured seconds; update it when a section gets slow).
  The parent prints each shard's output in turn and exits 1 on any FAIL. `--jobs=1` runs everything in one process; `--only=<regex>`
  runs the matching sections in one process (the dev loop); `--times` lists the slowest sections.
- **Landscape (UX-L1).** `landscape 740x360`, `844x390` and `1280x720 (browser, UX-L1)`: per size, a fresh game walks the whole first
  session pressing only what the guide points at (every target on screen and on top), then the rail, top row, stage (whole-pixel zoom),
  bar (Attack bottom right), each tab's menu with the bar still live, notices, the picker, the Attack sheet, Training and the gatherer
  board, and no sideways scroll. Portrait keeps its own sections at 360x740.
- **No flaky waits.** A check never races the live frame loop. Browser sections that need a state (a wind-up, a cooldown, a step)
  freeze the loop or drive `tick()` themselves and read the state, instead of waiting longer.

## Commands

```
node tools/build.mjs                         # build dist/lanternfall.html
node tools/check.mjs                         # every check on the SOLO build (the shipped game); 4 parallel shards, ~2.5 min. --only=<regex> one section, --jobs=1, --times; --party = the legacy party checks only
node tools/sim.mjs --policy mixed --hours 2 --seed 1   # balance timeline (policy fight|mixed, --every MIN)
node tools/sim.mjs --days 30 --class warden          # normal play over days (check-ins + away gains), docs/design/pacing.md
node tools/sim.mjs --days 20 --class ranger --evo trapper   # S3: evolve as soon as the Proving opens (Fenmother + level 35)
node tools/sim.mjs --report early [--seeds 3]        # SOLO1: the three starters, idle and active, 1 h mixed play: first boss, zone 5, zone 10 (E1-E6); --targets runs it first; --party 1 = the old party game
node tools/sim.mjs --targets                          # PASS/FAIL for T1-T18, D1, P1-P4 (docs/design/pacing.md, party-and-classes.md 9) and the recruit table; retune with --pace/--tune/--unlock/--combat/--enemy k=v
node tools/sim.mjs --class warden --lineup hesketh,wren,pip --t5 1 --t6 1 --t8 1   # a fixed line-up; party combat forks at 2h (T5 wipes, T6 hold zones, T8 offline vs live)
node tools/sim.mjs --report skills [--days 30]  # GP1: time to each gathering tier (focused, hours) and the day each skill opens each tier in normal play
node tools/sim.mjs --report econ [--days 45] [--class warden]   # ECON-A: EC1-EC13 over the three profiles (--profile idle|normal|active on any --days run; --upshare 0.35 the Blade budget)
node tools/sim.mjs --report hands [--days 35]   # N1: HS9-HS12, HS17, units per family by source, hires by rarity (--hands 0 turns Hands off anywhere)
node tools/heroart.mjs                       # HEROART1: repack art/heroes into src/js/21y-data-heroart.js (--check: up to date?)
node tools/perf.mjs --quick                  # frame, load, tap and memory benchmark vs the budget (docs/design/perf.md)
node tools/serve.mjs [port]                  # serve dist/ at http://localhost:5173 (launch config "lanternfall")
```
